# 基于人工智能的客户服务机器人——项目设计方案

## 一、项目概述

本项目面向企业在线客服场景，设计并实现一个融合大语言模型（LLM）、检索增强生成（RAG）和智能体（Agent）技术的客户服务机器人系统。系统采用前后端分离架构，前端基于React构建交互界面，后端采用Python FastAPI处理业务逻辑，AI服务层通过LangChain框架统一编排模型调用、知识库检索和智能体任务执行，实现从"你问我答"到"能理解、能检索、能办事"的智能客服能力跃升。

### 2.1 前端交互层

基于React框架构建，采用组件化开发模式，主要包含三个功能区域：

- **聊天窗口组件**：消息气泡展示、流式文本输出、输入框与发送控制、会话列表与切换
- **知识库管理组件**：文档上传（支持PDF/Word/TXT）、文档列表与状态查看、知识库检索测试
- **系统管理组件**：用户登录与权限控制、系统参数配置、对话记录查看

前端通过Axios发起HTTP请求与后端通信，消息接收采用Server-Sent Events（SSE）实现流式输出，用户可实时看到模型逐字生成的回复。

### 2.2 后端业务服务层

采用Python FastAPI框架，利用其原生异步支持处理客服场景的并发请求。核心模块包括：

- **用户管理模块**：用户注册、登录鉴权（JWT令牌）、角色权限（普通用户/管理员）
- **会话管理模块**：会话创建与关闭、消息持久化、对话历史加载
- **文档管理模块**：文档上传与存储、文档解析与分块、向量索引构建与更新
- **AI服务调度模块**：根据请求类型路由到对话链、RAG链或Agent工作流，管理模型调用和结果返回

后端通过依赖注入方式组织代码，各模块间通过接口解耦，便于单独测试和替换。

### 2.3 AI服务层

AI服务层是系统的核心，基于LangChain 1.x框架统一编排，包含三条处理链路：

#### 2.3.1 对话链（Dialogue Chain）

采用LCEL（LangChain Expression Language）编排，流程为：

```
用户输入 → 提示模板填充 → 对话历史注入 → LLM调用 → 流式输出
```

提示模板包含系统角色设定（你是一个专业的客服助手）、对话格式规范和业务约束条件。对话历史通过LangChain的ConversationBufferWindowMemory管理，保留最近N轮对话，超出部分自动截断，兼顾上下文完整性和Token消耗控制。

#### 2.3.2 RAG问答链（RAG QA Chain）

完整流程覆盖文档处理到检索问答的全链路：

**文档处理阶段**：
1. 文档加载：通过LangChain的DocumentLoader支持PDF、Word、TXT等格式
2. 文本分块：采用RecursiveCharacterTextSplitter，按段落和句子边界切分，块大小512字符，重叠64字符
3. 向量化：调用Embedding模型将文本块转为向量
4. 存储：向量存入Chroma数据库，同时保留原始文本和元数据（来源文档、页码等）

**检索问答阶段**：
1. 用户提问 → 问题向量化 → Chroma相似度检索（Top-K=4）
2. 检索结果 + 问题 → 提示模板组装 → LLM生成回答
3. 回答附带来源引用，标注信息出自哪份文档的哪个段落

#### 2.3.3 Agent工作流（Agent Workflow）

基于LangGraph构建状态图，实现条件分支和工具调用：

```
用户输入 → 意图识别 → [简单问答] → 直接对话链
                    → [知识查询] → RAG检索工具
                    → [业务操作] → 订单查询/业务办理工具
                    → [无法判断] → 追问澄清
```

预定义工具集：
- **知识库查询工具**：调用RAG链检索企业知识文档
- **订单查询工具**：根据订单号查询订单状态（模拟接口）
- **业务办理工具**：执行退货申请、修改地址等操作（模拟接口）
- **转人工工具**：当Agent判断无法处理时，触发转人工通知

Agent通过LangGraph的StateGraph定义状态节点和转移条件，每个节点是一个处理步骤，边上的条件函数决定下一步走向。这种图结构比纯链式调用更灵活，支持循环（如追问后重新判断意图）和并行（同时调用多个工具）。

### 2.4 数据存储层

- **MySQL**：存储用户信息、会话记录、消息内容、文档元数据等结构化数据
- **Chroma**：存储文档分块的向量表示，支持相似度检索
- **文件系统**：存储原始文档文件，路径信息记录在MySQL中

## 五、关键技术方案

### 5.1 流式输出方案

用户发送消息后，后端通过SSE（Server-Sent Events）将LLM的流式输出逐块推送到前端。FastAPI使用StreamingResponse配合async生成器实现，前端通过EventSource API接收并实时渲染。这样用户无需等待完整回复生成，体验更接近真人客服的逐字回复效果。

### 5.2 知识库更新策略

文档上传后触发异步处理流程：解析→分块→向量化→入库。Chroma支持增量添加，新文档的向量可直接追加到已有集合中，无需重建整个索引。文档删除时，通过元数据过滤移除对应向量。为保证检索时效性，文档处理完成后立即更新Chroma集合，用户下次提问即可检索到新内容。

### 5.3 Agent工具调用决策

Agent的意图识别依赖LLM自身的判断能力，通过提示模板中明确描述各工具的适用场景来引导决策。例如："当用户询问业务规则、产品信息时，使用知识库查询工具；当用户提供订单号或询问物流状态时，使用订单查询工具"。同时设置兜底策略：当Agent连续两次无法确定意图时，主动询问用户澄清，避免无效循环。

### 5.4 对话历史管理

采用滑动窗口策略，保留最近10轮对话（可配置）。历史消息存储在MySQL中，每次对话开始时从数据库加载，注入到LangChain的Memory组件。窗口外的历史消息不丢弃，仅不注入当前上下文，用户可随时在界面中查看完整对话记录。
